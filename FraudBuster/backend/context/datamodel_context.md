# Data Model Context Summary

This file is a compact handover for the **Transaction Monitoring & Alerts** database model so it can be reused as context later.

---

## 1) Current project scope

- Backend database: **MySQL**
- Domain: **ecommerce transaction monitoring layer** sitting between payment service and payment gateway
- Current MVP assumptions:
  - dummy/static data first
  - no authentication
  - single operator workflow
  - alert lifecycle and hold-window are key requirements

---

## 2) Core business flow

`Customer Checkout -> Payment Service -> Monitoring Layer -> Payment Gateway`

The database must support:
- transaction intake
- rule evaluation
- alert generation
- alert lifecycle management
- alert history and audit trail
- hold/release/decline decisions

---

## 3) Confirmed alert lifecycle

Lifecycle:

`OPEN -> ACKNOWLEDGED -> INVESTIGATING -> CLOSED`

False-positive path:

`OPEN / ACKNOWLEDGED / INVESTIGATING -> DISMISSED`

### Hold window policy
- Operator gets **10 minutes** to investigate
- Payment can be held during this time
- If investigation result is **true positive** -> **DECLINE** transaction
- If investigation result is **false positive** -> **RELEASE / ALLOW** transaction
- If **no decision within 10 minutes** -> **AUTO-DECLINE**

---

## 4) Recommended tables

### A. `transactions`
Stores each monitored payment event.

Typical columns:
- `id` BIGINT PK
- `txn_id` VARCHAR UNIQUE
- `account_id` VARCHAR
- `customer_full_name` VARCHAR(120)
- `customer_email` VARCHAR(150)
- `customer_phone` VARCHAR(20)
- `payee_id` VARCHAR
- `amount` DECIMAL(18,2)
- `currency` CHAR(3)
- `txn_type` ENUM('DEBIT','CREDIT')
- `txn_timestamp` DATETIME(3)
- `monitor_state` ENUM('RECEIVED','HELD','RELEASED','DECLINED')
- `hold_started_at` DATETIME(3)
- `hold_expires_at` DATETIME(3)
- `final_decision` ENUM('PENDING','ALLOW','DECLINE')
- `decision_reason` VARCHAR(120)
- `decided_at` DATETIME(3)
- `created_at`, `updated_at`

Why it exists:
- source of truth for each transaction
- supports dashboard counts and transaction list page
- stores inline decision and hold-window fields
- stores customer contact details for operator verification calls
- stores all monitored transactions, not only those that generated alerts

MVP implementation notes:
- customer details in this table are limited to `customer_full_name`, `customer_email`, and `customer_phone`
- `txn_type` remains `DEBIT`/`CREDIT`, but current ecommerce payment-path rules are primarily evaluated for `DEBIT`

---

### B. `rules`
Stores monitoring rules/configuration.

Typical columns:
- `id` BIGINT PK
- `rule_code` VARCHAR UNIQUE
- `name` VARCHAR
- `rule_type` ENUM('AMOUNT_THRESHOLD','VELOCITY','NEW_PAYEE','DAILY_LIMIT','CUSTOM')
- `severity_default` ENUM('LOW','MEDIUM','HIGH')
- `inline_mode` ENUM('INLINE_BLOCKING','ASYNC')
- `config_json` JSON
- `is_active` TINYINT(1)
- `is_deleted` TINYINT(1)
- `created_at`, `updated_at`

Why it exists:
- central place for rule definitions
- supports rules page with toggle/edit
- allows future rule configuration changes without code changes

---

### C. `alerts`
Stores detected incidents generated by rules.

Typical columns:
- `id` BIGINT PK
- `alert_id` VARCHAR UNIQUE
- `rule_id` BIGINT FK -> `rules.id`
- `severity` ENUM('LOW','MEDIUM','HIGH')
- `status` ENUM('OPEN','ACKNOWLEDGED','INVESTIGATING','CLOSED','DISMISSED')
- `title` VARCHAR
- `description` TEXT
- `opened_at` DATETIME(3)
- `acknowledged_at` DATETIME(3)
- `investigating_at` DATETIME(3)
- `closed_at` DATETIME(3)
- `dismissed_at` DATETIME(3)
- `sla_expires_at` DATETIME(3)
- `timeout_auto_decline` TINYINT(1)
- `resolution_notes` TEXT
- `created_at`, `updated_at`

Why it exists:
- separates alert incident tracking from raw transaction data
- supports alert list, alert detail panel, and history page
- tracks lifecycle timestamps and 10-minute SLA

---

### D. `alert_transactions`
Junction table between alerts and transactions.

Typical columns:
- `id` BIGINT PK
- `alert_fk` BIGINT FK -> `alerts.id`
- `transaction_fk` BIGINT FK -> `transactions.id`
- `link_type` ENUM('PRIMARY','RELATED')
- `trigger_snapshot` JSON
- `created_at` DATETIME(3)

Why it exists:
- supports many-to-many relation
- one alert can involve multiple transactions
- one transaction can trigger multiple alerts

Unique constraint:
- `UNIQUE(alert_fk, transaction_fk)`

---

### E. `alert_status_history`
Stores status transition history.

Typical columns:
- `id` BIGINT PK
- `alert_fk` BIGINT FK -> `alerts.id`
- `from_status` ENUM(...)
- `to_status` ENUM(...)
- `changed_by_type` ENUM('OPERATOR','SYSTEM')
- `changed_by_ref` VARCHAR(80)
- `comment` VARCHAR(255)
- `changed_at` DATETIME(3)

Why it exists:
- audit trail of alert lifecycle changes
- useful for history/debugging/compliance

---

### F. `alert_actions`
Stores operator/system actions performed on an alert.

Typical columns:
- `id` BIGINT PK
- `alert_fk` BIGINT FK -> `alerts.id`
- `action_type` ENUM('ACKNOWLEDGE','INVESTIGATE','CLOSE','DISMISS','ADD_NOTE','AUTO_TIMEOUT_DECLINE')
- `action_note` TEXT
- `actor_type` ENUM('OPERATOR','SYSTEM')
- `actor_ref` VARCHAR(80)
- `created_at` DATETIME(3)

Why it exists:
- action log separate from status history
- helps trace who did what and when

---

### G. `transaction_decisions`
Stores hold/release/decline outcomes for transactions.

Typical columns:
- `id` BIGINT PK
- `transaction_fk` BIGINT FK -> `transactions.id`
- `alert_fk` BIGINT FK -> `alerts.id` NULL allowed
- `decision` ENUM('HOLD','RELEASE','DECLINE')
- `decision_source` ENUM('RULE_ENGINE','OPERATOR','AUTO_TIMEOUT','SYSTEM')
- `reason_code` VARCHAR(60)
- `reason_text` VARCHAR(255)
- `decided_at` DATETIME(3)

Why it exists:
- explicit audit trail for payment-path outcome
- supports the 10-minute hold policy and auto-decline logic

---

## 5) Relationships and cardinality

- `rules (1) -> (N) alerts`
- `alerts (N) <-> (N) transactions` via `alert_transactions`
- `alerts (1) -> (N) alert_status_history`
- `alerts (1) -> (N) alert_actions`
- `transactions (1) -> (N) transaction_decisions`
- `alerts (1) -> (N) transaction_decisions` when a decision is linked to a specific alert

This means:
- one transaction can trigger multiple alerts
- one alert can relate to multiple transactions
- lifecycle and audit history are preserved separately

---

## 6) Important modeling note: New Payee vs High Value Transfer

- These two rules are **independent** by default
- There is **no direct dependency** between them
- A single transaction may trigger both at the same time
- In that case, risk can be escalated by severity or a composite rule later

Example:
- `New Payee` triggers because payee is first-time
- `High Value Transfer` triggers because amount exceeds threshold
- same transaction can create 2 alerts

## 7) Practical indexes to remember

### `transactions`
- `UNIQUE(txn_id)`
- `INDEX(account_id, txn_timestamp)`
- `INDEX(customer_email)`
- `INDEX(customer_phone)`
- `INDEX(payee_id, txn_timestamp)`
- `INDEX(monitor_state, txn_timestamp)`
- `INDEX(txn_timestamp)`

### `rules`
- `UNIQUE(rule_code)`
- `INDEX(is_active, is_deleted, rule_type)`

### `alerts`
- `UNIQUE(alert_id)`
- `INDEX(status, severity, opened_at)`
- `INDEX(opened_at)`
- `INDEX(closed_at)`
- `INDEX(rule_id, opened_at)`
- `INDEX(sla_expires_at, status)`

### `alert_transactions`
- `UNIQUE(alert_fk, transaction_fk)`
- `INDEX(transaction_fk)`
- `INDEX(alert_fk)`

### `alert_status_history`
- `INDEX(alert_fk, changed_at)`

### `alert_actions`
- `INDEX(alert_fk, created_at)`

### `transaction_decisions`
- `INDEX(transaction_fk, decided_at)`
- `INDEX(decision_source, decided_at)`

---

## 8) Short summary

We need a MySQL model centered on `transactions`, `rules`, `alerts`, and `alert_transactions`, with extra audit/history tables for alert lifecycle and transaction decisions. It must support many-to-many alert/transaction relationships, 10-minute hold window logic, auto-decline, and UI queries for dashboard, alerts, transactions, rules, and history.

Additional MVP decisions finalized:
- keep all incoming monitored transactions in `transactions` (do not keep only alerted transactions)
- link suspicious events through `alerts` + `alert_transactions`
- use customer contact fields in alert workflows for operator verification calls
