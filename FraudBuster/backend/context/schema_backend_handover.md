# FraudBuster Backend Start Context

Read this file first when starting backend work. It is the compact source-of-truth for the MVP schema and flow. For deeper field explanations and examples, read `schema_backend_details.md` only when needed.

## Scope

FraudBuster is an ecommerce transaction monitoring layer between payment service and payment gateway.

```text
Customer checkout -> Payment service -> FraudBuster -> Payment gateway
```

MVP rules:

- Java Spring Boot backend, MySQL database.
- No auth yet; use text actors like `SYSTEM` and `operator-1`.
- Rules are seeded/system-defined in MVP; operators do not edit rules.
- Operators only review alerts, add actions/notes, and allow/decline transactions.
- Inline suspicious transactions can be held for 10 minutes.
- Fraud confirmed -> `DECLINE`.
- False positive -> `ALLOW` / release.
- No decision within 10 minutes -> auto-decline.

## Tables

`transactions`

- Stores every monitored transaction.
- Business id: `txn_id`.
- Current monitoring fields: `monitor_state`, `final_decision`, `decision_reason`, `decided_at`.
- Hold fields: `hold_started_at`, `hold_expires_at`.
- Customer verification fields: `customer_full_name`, `customer_email`, `customer_phone`.

`rules`

- Master/config table for fraud rules.
- Seeded by default for MVP.
- Active rule filter: `is_active = TRUE AND is_deleted = FALSE`.
- `severity_default` is copied to `alerts.severity`.
- `inline_mode = INLINE` can hold payment; `POST_AUTH` creates monitoring alert after payment.
- Rule examples: `HIGH_VALUE`, `VELOCITY_10M`, `NEW_DEVICE`.

`alerts`

- Runtime suspicious case generated by a matched rule.
- FK: `alerts.rule_id -> rules.id`.
- Current lifecycle state is stored in `alerts.status`.
- Lifecycle: `OPEN -> ACKNOWLEDGED -> INVESTIGATING -> CLOSED`.
- False positive path: `OPEN/ACKNOWLEDGED/INVESTIGATING -> DISMISSED`.

`alert_transactions`

- Bridge table between alerts and transactions.
- FK: `alert_transactions.alert_id -> alerts.id`.
- FK: `alert_transactions.transaction_id -> transactions.id`.
- Unique pair: `UNIQUE(alert_id, transaction_id)`.
- `relation_type` tells transaction role:
  - `TRIGGERING_TRANSACTION`: directly caused the rule hit.
  - `RELATED_TRANSACTION`: supporting transaction in grouped alerts.

`alert_status_history`

- Audit table for every alert status change.
- Stores `old_status`, `new_status`, `changed_by`, `change_reason`, `changed_at`.
- Insert a row every time `alerts.status` changes.

`alert_actions`

- Investigation activity timeline.
- Stores operator/system actions like `NOTE_ADDED`, `CUSTOMER_VERIFIED`, `TRANSACTION_RELEASED`, `TRANSACTION_DECLINED`, `ESCALATED`.
- Different from status history: this records what work happened, not only status transitions.

`transaction_decisions`

- Final allow/decline audit for transactions.
- FK: `transaction_decisions.transaction_id -> transactions.id`.
- Optional FK: `transaction_decisions.alert_id -> alerts.id`.
- `decision` is `ALLOW` or `DECLINE`.
- Also mirror final result into `transactions.final_decision`, `monitor_state`, `decision_reason`, and `decided_at`.

## Relationships

```text
rules 1 -> N alerts
alerts N -> N transactions through alert_transactions
alerts 1 -> N alert_status_history
alerts 1 -> N alert_actions
transactions 1 -> N alert_actions, optional
transactions 1 -> N transaction_decisions
alerts 1 -> N transaction_decisions, optional link
```

## Runtime Flow

```text
1. Transaction arrives.
2. Insert row in transactions.
3. Load active, non-deleted rules.
4. Evaluate rules against transaction.
5. If rule matches, create alerts row.
6. Link alert to transaction(s) in alert_transactions.
7. Insert initial alert_status_history row: NULL -> OPEN by SYSTEM.
8. Operator acknowledges/investigates alert.
9. Each status change updates alerts.status and inserts alert_status_history.
10. Operator actions/notes go into alert_actions.
11. Final ALLOW/DECLINE goes into transaction_decisions.
12. Mirror final decision onto transactions.
13. Close confirmed fraud alerts as CLOSED; false positives as DISMISSED.
```

## Backend Implementation Order

```text
1. Entity classes
2. Repository interfaces
3. Read APIs: dashboard, transactions, alerts, rules
4. Alert lifecycle APIs: acknowledge, investigate, close, dismiss
5. Alert action API: add note, customer verified, released, declined
6. Transaction decision APIs: allow, decline
7. Rule evaluation service
8. Timeout job for held transactions past hold_expires_at
```

## Mental Model

```text
rules = fraud policy/config
transactions = incoming payment events
alerts = suspicious cases generated by rules
alert_transactions = which transactions are involved in each alert
alert_status_history = alert status audit
alert_actions = operator/system investigation activity
transaction_decisions = final allow/decline audit
```
