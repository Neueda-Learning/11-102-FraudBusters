# FraudBuster Schema Details

Read this only when extra explanation is needed. The compact backend-start file is `schema_backend_handover.md`.

## Field Details

### transactions

- `id`: internal primary key used by foreign keys.
- `txn_id`: external/business transaction id shown in APIs/UI.
- `account_id`: customer/account identifier used for velocity checks.
- `customer_full_name`: operator can use this during verification.
- `customer_email`: operator can use this during verification/search.
- `customer_phone`: operator can use this during verification/search.
- `payee_id`: merchant/payee identifier, useful for payee-based rules.
- `amount`: transaction amount used by amount threshold rules.
- `currency`: transaction currency, default `USD`.
- `txn_type`: `DEBIT` or `CREDIT`; ecommerce payment monitoring mainly uses `DEBIT`.
- `txn_timestamp`: actual transaction time, used by time-window rules.
- `monitor_state`: current monitoring state: `RECEIVED`, `HELD`, `RELEASED`, `DECLINED`.
- `hold_started_at`: when an inline hold started.
- `hold_expires_at`: when the 10-minute hold expires.
- `final_decision`: current transaction decision: `PENDING`, `ALLOW`, `DECLINE`.
- `decision_reason`: latest reason displayed on transaction details.
- `decided_at`: when the final decision was made.
- `created_at`, `updated_at`: database audit timestamps.

### rules

- `id`: internal primary key.
- `rule_code`: stable machine-readable code, for example `HIGH_VALUE`.
- `name`: display name for UI/logs.
- `description`: human-readable rule explanation.
- `rule_type`: category like `AMOUNT`, `VELOCITY`, `NEW PAYEE`.
- `severity_default`: severity copied into an alert when this rule triggers.
- `inline_mode`: `INLINE` or `POST_AUTH`.
- `config_json`: rule-specific thresholds/config.
- `is_active`: if `TRUE`, rule participates in evaluation; if `FALSE`, rule is paused.
- `is_deleted`: soft-delete flag; deleted rules should not be used for new evaluation.
- `created_at`, `updated_at`: audit timestamps.

`inline_mode`:

- `INLINE`: evaluated before final payment decision; can hold transaction.
- `POST_AUTH`: evaluated after transaction acceptance for monitoring/audit.

### alerts

- `id`: internal primary key.
- `alert_code`: stable alert identifier shown in dashboard/logs.
- `rule_id`: foreign key to `rules.id`; tells which rule generated the alert.
- `severity`: copied from `rules.severity_default` at alert creation time.
- `status`: current operator workflow status.
- `risk_score`: optional numeric risk score for sorting priority alerts.
- `title`: short operator-facing summary.
- `description`: supporting details for the alert.
- `hold_expires_at`: hold deadline for inline alerts.
- `closed_at`: when investigation was closed/dismissed.
- `closure_reason`: final explanation when alert is closed/dismissed.
- `created_at`, `updated_at`: audit timestamps.

### alert_transactions

- `id`: internal primary key.
- `alert_id`: FK to `alerts.id`.
- `transaction_id`: FK to `transactions.id`.
- `relation_type`: transaction role inside the alert.
- `created_at`: when the link was created.

`relation_type` examples:

- `TRIGGERING_TRANSACTION`: the transaction directly caused the alert.
- `RELATED_TRANSACTION`: the transaction gives context to a grouped alert.

### alert_status_history

- `id`: internal primary key.
- `alert_id`: FK to `alerts.id`.
- `old_status`: previous status; `NULL` for initial creation.
- `new_status`: new alert status.
- `changed_by`: `SYSTEM`, `operator-1`, or similar display text for MVP.
- `change_reason`: reason for the status change.
- `changed_at`: when the transition happened.

Reason ownership:

- System-generated status changes have autogenerated `change_reason`.
- Operator status changes can use default text for simple transitions.
- Final `CLOSED` or `DISMISSED` should require a meaningful operator reason.

### alert_actions

- `id`: internal primary key.
- `alert_id`: FK to `alerts.id`.
- `transaction_id`: optional FK to `transactions.id`, used when action is about a specific transaction.
- `action_type`: `NOTE_ADDED`, `CUSTOMER_VERIFIED`, `TRANSACTION_RELEASED`, `TRANSACTION_DECLINED`, `ESCALATED`.
- `performed_by`: `SYSTEM`, `operator-1`, or similar display text for MVP.
- `action_note`: human-readable note/details.
- `performed_at`: when the action happened.

### transaction_decisions

- `id`: internal primary key.
- `transaction_id`: FK to `transactions.id`.
- `alert_id`: optional FK to `alerts.id`; nullable for future non-alert decisions.
- `decision`: `ALLOW` or `DECLINE`.
- `decided_by`: `SYSTEM`, `operator-1`, or similar display text for MVP.
- `decision_reason`: final business reason.
- `decided_at`: when the final decision happened.

## Examples

### High Value Alert

```text
Transaction amount = 150000
Rule HIGH_VALUE threshold = 100000
Rule triggers

alerts:
rule_id = HIGH_VALUE rule id
severity = HIGH
status = OPEN
hold_expires_at = now + 10 minutes

alert_transactions:
alert_id = created alert id
transaction_id = triggering transaction id
relation_type = TRIGGERING_TRANSACTION
```

### Velocity Alert

```text
Same account has 6 transactions in 10 minutes.
The 6th transaction triggers the alert.

alert_transactions:
T6 -> TRIGGERING_TRANSACTION
T1 to T5 -> RELATED_TRANSACTION
```

### Status History

```text
Alert created:
old_status = NULL
new_status = OPEN
changed_by = SYSTEM
change_reason = Alert created after HIGH_VALUE rule matched.

Operator acknowledges:
old_status = OPEN
new_status = ACKNOWLEDGED
changed_by = operator-1
change_reason = Operator started review.

Operator investigates:
old_status = ACKNOWLEDGED
new_status = INVESTIGATING
changed_by = operator-1
change_reason = Checking customer transaction pattern.

Operator closes:
old_status = INVESTIGATING
new_status = CLOSED
changed_by = operator-1
change_reason = Fraud confirmed, transaction declined.
```

### Alert Actions vs Transaction Decisions

`alert_actions` is the investigation diary:

```text
NOTE_ADDED: Amount is unusually high for this customer.
CUSTOMER_VERIFIED: Customer could not confirm this transaction.
TRANSACTION_DECLINED: Declined after high-value alert review.
```

`transaction_decisions` is the final judgement:

```text
transaction_id = T3
alert_id = A1
decision = DECLINE
decided_by = operator-1
decision_reason = Fraud risk confirmed after reviewing high-value transaction.
```

When a decision row is created, update `transactions` too:

```text
DECLINE:
transactions.monitor_state = DECLINED
transactions.final_decision = DECLINE

ALLOW:
transactions.monitor_state = RELEASED
transactions.final_decision = ALLOW
```
